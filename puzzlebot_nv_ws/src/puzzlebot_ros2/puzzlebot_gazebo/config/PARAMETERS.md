# gazebo_bridge.yaml Parameters Guide

This document explains the parameters in `gazebo_bridge.yaml`:
- where they come from,
- why they are needed, and
- what data direction each bridge uses.

## What this file is

`gazebo_bridge.yaml` is a configuration file for `ros_gz_bridge` (`parameter_bridge`).
The launch file loads it here:

- `puzzlebot_gazebo/launch/puzzlebot_gazebo.launch.xml`
  - node: `ros_gz_bridge parameter_bridge`
  - parameter: `config_file := puzzlebot_gazebo/config/gazebo_bridge.yaml`

So this YAML is the contract between ROS 2 topics and Gazebo Transport topics.

## Where these parameters come from

Each bridge entry in this file follows the schema expected by `ros_gz_bridge`:

- `ros_topic_name`: ROS 2 topic name.
- `gz_topic_name`: Gazebo topic name.
- `ros_type_name`: ROS 2 message type.
- `gz_type_name`: Gazebo message type.
- `direction`: transfer direction.

In this project, topic names are chosen to match:
- simulation producers in Gazebo (clock, odom/tf, scan, model states),
- motion commands from ROS 2 (`/cmd_vel`),
- navigation stack expectations (`/odom`, `/scan`, `/tf`, `/clock`).

## Direction values

- `GZ_TO_ROS`: Gazebo publishes, ROS 2 receives.
- `ROS_TO_GZ`: ROS 2 publishes, Gazebo receives.

Mental model:
- Sensors and sim state usually go `GZ_TO_ROS`.
- Commands usually go `ROS_TO_GZ`.

## Entry-by-entry explanation

## 1) Clock

```yaml
- ros_topic_name: "/clock"
  gz_topic_name: "/clock"
  ros_type_name: "rosgraph_msgs/msg/Clock"
  gz_type_name: "gz.msgs.Clock"
  direction: GZ_TO_ROS
```

- Source: Gazebo simulation time.
- Why: all ROS 2 nodes using `use_sim_time=true` must read `/clock`.
- Direction: Gazebo is the time authority, so data flows `GZ_TO_ROS`.

## 2) Velocity command

```yaml
- ros_topic_name: "/cmd_vel"
  gz_topic_name: "/cmd_vel"
  ros_type_name: "geometry_msgs/msg/Twist"
  gz_type_name: "gz.msgs.Twist"
  direction: ROS_TO_GZ
```

- Source: ROS 2 controllers, teleop, or Nav2.
- Why: robot motion command must reach Gazebo drive system.
- Direction: command originates in ROS 2, so `ROS_TO_GZ`.

## 3) Odometry

```yaml
- ros_topic_name: "/odom"
  gz_topic_name: "/odom"
  ros_type_name: "nav_msgs/msg/Odometry"
  gz_type_name: "gz.msgs.Odometry"
  direction: GZ_TO_ROS
```

- Source: Gazebo kinematics / drive simulation.
- Why: localization and navigation depend on odometry.
- Direction: simulated odom is produced in Gazebo, so `GZ_TO_ROS`.

## 4) TF from diff drive

```yaml
- ros_topic_name: "/tf"
  gz_topic_name: "/diff_drive/tf"
  ros_type_name: "tf2_msgs/msg/TFMessage"
  gz_type_name: "gz.msgs.Pose_V"
  direction: GZ_TO_ROS
```

- Source: Gazebo diff-drive transform stream.
- Why: ROS 2 consumers expect TF on `/tf`.
- Why names differ: Gazebo side uses `/diff_drive/tf`; ROS side standardizes to `/tf`.
- Direction: transform is generated by Gazebo, so `GZ_TO_ROS`.

## 5) Joint states

```yaml
- ros_topic_name: "/joint_states"
  gz_topic_name: "/joint_states"
  ros_type_name: "sensor_msgs/msg/JointState"
  gz_type_name: "gz.msgs.Model"
  direction: GZ_TO_ROS
```

- Source: Gazebo model/joint simulation.
- Why: ROS tools and state consumers use `/joint_states`.
- Direction: simulation state comes from Gazebo, so `GZ_TO_ROS`.

## 6) Laser scan

```yaml
- ros_topic_name: "/scan"
  gz_topic_name: "/scan"
  ros_type_name: "sensor_msgs/msg/LaserScan"
  gz_type_name: "gz.msgs.LaserScan"
  direction: GZ_TO_ROS
```

- Source: simulated lidar sensor.
- Why: SLAM and Nav2 require scan input.
- Direction: sensor data originates in Gazebo, so `GZ_TO_ROS`.

## How this connects to the rest of the stack

- `puzzlebot_navigation2` expects topics like `/odom` and `/scan`.
- `use_sim_time=true` across launch files depends on the `/clock` bridge.
- `/cmd_vel` is the control input path from ROS 2 to simulation.

Without this bridge mapping, ROS 2 and Gazebo are running but isolated.

## How to change safely

When adding or editing entries:

1. Keep topic names consistent with both producer and consumer.
2. Keep message types exactly matched (`ros_type_name` <-> `gz_type_name`).
3. Choose direction based on where the message is produced.
4. Restart the launch after edits (bridge reads config on startup).

## Quick verification checklist

After launching simulation:

1. `ros2 topic list` should include `/clock`, `/cmd_vel`, `/odom`, `/tf`, `/joint_states`, `/scan`.
2. `ros2 topic echo /clock` should show time updates.
3. Publishing a `Twist` on `/cmd_vel` should move the robot.
4. `ros2 topic echo /scan` and `/odom` should stream data.

If a topic exists but has no data, the common causes are:
- wrong topic name on one side,
- wrong message type mapping,
- wrong direction.
